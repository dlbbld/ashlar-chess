# 20.0.0 — JPMS module boundary & public API surface — release plan (DRAFT)

> **Status:** draft for review by Daniel + Codex. 2026-06-21.
> Nothing here is committed to scope yet; the **open decisions in §5** must be resolved before
> `module-info.java` freezes them.

---

## 0. One-paragraph recommendation

JPMS is **medium-high urgency, not panic**. It fixes no bug — classpath users are fine today. What it
fixes is that the *published contract* is currently accidental: the module is named `ashlar.chess` by
filename luck, and every one of 153 public types is reachable whether or not it was meant to be API. Now
that 19.0.0 carved a real shape, that accidental surface is the thing reviewers keep flagging. The plan
splits into a **cheap, near-zero-risk name fix that should ship almost immediately** (possibly as
`19.0.1`) and the **deliberate boundary work** that is the body of 20.0.0. The boundary work *describes*
the carved stone — it does not re-carve it. The only genuine re-carving (sentinel-record redesign,
`common.*` renames) is bundled in only because it is breaking and a major bump is the one honest moment to
do it.

## 2. The two moves, and why they are independent

A JPMS-newbie framing that drives the whole plan:

- **`Automatic-Module-Name` commits the *name* only.** It says "when someone writes `requires <name>;`,
  this is the name" — and nothing about which packages are visible. As an automatic module the *whole jar*
  stays readable. One manifest line. No code change. No classpath break.
- **`module-info.java` commits the *exports*.** It turns exported packages into a formal contract and makes
  every non-exported package *inaccessible* to named-module consumers. This is the real work, because it
  forces the question "is this package API, or just `public` because Java made that convenient?"

They are **independent**. We can lock the intentional name today and decide exports later. The eventual
`module-info` simply adopts the name already committed — no second rename.

---

## 3. ⏰ The one time-sensitive item: fix the module name now

Changing a module's name *is* a breaking change for anyone who already wrote `requires ashlar.chess;`. The
library was first published as 19.0.0 **today**, so realistically **no one depends on the accidental name
yet** — which is exactly why this is the one item that gets *more* expensive every week we wait.

**Proposal:** ship as a `19.0.1` patch (additive manifest metadata, zero behavior change), ahead of and
separate from the 20.0.0 boundary work:

```xml
<!-- maven-jar-plugin → <archive> → <manifestEntries>, alongside the existing entries -->
<Automatic-Module-Name>io.github.dlbbld.ashlarchess</Automatic-Module-Name>
```

- Name mirrors the base package (`io.github.dlbbld.ashlarchess`) — the reverse-DNS convention.
- Risk: ~zero. It only affects JPMS consumers, of which there are presumably none, and it does not constrain
  any future export decision.
- **Decision for review:** `19.0.1` now, or fold into 20.0.0? (Codex's "calm first strike" argument and the
  "nobody depends on it yet, but they will" window both favor *now*.)

**Newbie simplification worth banking:** under `module-info`, *not exporting* a package already hides it
from named-module consumers. We do **not** have to rename everything to `*.internal` to hide it. The
`*.internal` rename is a *signal* (helps plain-classpath users, kills "looks like API" ambiguity, enforces
no split packages) — it can be applied to only the worst offenders, or deferred. **This de-risks the release
substantially**: the hard guarantee comes from `exports`, not from a giant rename wave.

## 5. Open design calls — must be decided before `module-info` freezes them

1. **`BitboardPosition`** — public *advanced* API, or hide it and remove/replace `Board.getBitboardPosition()`?
   It is verified bit-exact and genuinely useful to analysis/ML users. *My lean:* keep it public but
   explicitly documented as advanced, low-level API — not hide it. Decide before export.

2. **Guava on the public surface** — several move-gen helpers and immutable returns currently expose Guava
   `Immutable*` types. If any *exported* method returns/accepts them, `module-info` needs
   `requires transitive com.google.common`, which **forces Guava onto every consumer's module graph**.
   *My lean for a top-tier library:* keep Guava strictly internal and return JDK immutables
   (`List.copyOf`/`Set.copyOf`) on the public surface — cleaner, dependency-free contract. This pairs with
   the §6 Phase-2 return-type tightening. Decide: leak Guava (transitive) vs. JDK-immutable public returns.
   **RESOLVED (2026-06-22): Guava removed entirely.** Went further than "keep internal" — the dependency is dropped
   from `pom.xml` and all internal use is replaced with JDK collections (order preserved via unmodifiable
   `LinkedHashSet`/`LinkedHashMap`/`EnumMap`, never `Set.copyOf`/`Map.copyOf`), so `module-info` needs no Guava
   `requires` at all. See the "Drop the Guava dependency" entry in `tasks.md`.

3. **Sentinel/tagged-union records → sealed hierarchy** (breaking; deferred from 19.0.0 by Codex).
   `MoveSpecification` encodes normal/promotion/castling via `Square.NONE`/`CastlingMove.NONE`/
   `PromotionPieceType.NONE` sentinels; `UciMove` carries redundant `text` + `isPromotion` +
   `promotionPieceType` that can disagree if built directly. Fix is a sealed
   `NormalMove`/`PromotionMove`/`CastlingMove` hierarchy. A major bump is the right moment.

4. **`common.*` package names** — `common.model`/`common.enums` are mechanically fine but inelegant as
   *public* package names. Decide cleaner domain homes for the types that stay public (the rest just go
   unexported/internal and the name matters less).

5. **`UciMoveUtility`** — public iff UCI conversion is a promised feature; if so, rehome under a cleaner
   package/name than `common.ucimove.utility`.

6. **Package-by-feature reset** (already in tasks.md) — collapse the duplicated by-kind buckets
   (`exceptions` **and** `common.exceptions`; `enums` **and** `common.enums`; `model` **and**
   `common.model`) and inline feature-specific types beside their feature. This is the **prerequisite** to a
   clean `module-info`: sensible `exports` are impossible while features are split across two `common.*` junk
   drawers.

## 6. Proposed execution order (each phase = one reviewable PR on the branch)

> Branch off `main`. Major bump → its own branch + Codex review on the remote, per workflow.

- **Phase 0 — module name.** `Automatic-Module-Name`. *Possibly shipped first as `19.0.1` (§3).* ~Zero risk.
- **Phase 1 — package-by-feature reset (§5.6).** Mechanical, compiler-checked, no behavior change. Collapse
  duplicate buckets, inline feature types. **Prerequisite** for clean exports. (FEN slice already landed in
  19.0.0; this is the global pass.)
- **Phase 2 — settle the classification table (§4) + tighten move-gen return types.** Fold the
  `performPromotionMovements`/`performCastlingMovements`/`performEnPassantCaptureMovements`/
  `EmptyBoardMoveUtility` return types (mutable → immutable) into the same pass that decides whether they stay
  public at all. Resolve the Guava call (§5.2) here.
- **Phase 3 — hide internals.** Primarily: just don't export. Optional `*.internal` rename for the most
  misleading packages only (keep it minimal — §4 note).
- **Phase 4 — breaking redesigns + additive API.** Sentinel→sealed hierarchy (§5.3). Position-as-value
  additions: public `mirror()` (vertical flip + colour swap — **not** `SquareUtility.flip`) and immutable
  `play(move) → position` (machinery already exists as `BitboardPosition.afterMove`). Design these together
  with the public position type the boundary settles on.
- **Phase 5 — add `module-info.java`.** `exports` only the agreed public packages; `requires` per §1.
- **Phase 6 — Maven test config (the fiddly part, §7).** `--patch-module` + a few `--add-exports`.
- **Phase 7 — verify & ship.** Full suite (`-Pfull`), `javadoc:javadoc -Dshow=private`, then the 20.0.0
  release flow (remember the `central-publishing-maven-plugin` 0.7.0→0.11.0 bump before deploy).

## 7. The Maven test-config detail (newbie-relevant, highest-effort part)

**Why it's fiddly:** the test suite is deliberately *white-box* — tests live in the same packages as the
code and reach internals cross-package (that's how a differential-test library verifies its own guts). The
moment `module-info` exists, the main artifact is a *named module* and its non-exported packages become
inaccessible — including to the tests. Two standard ways through, in order of preference:

1. **Patch tests into the main module (recommended).** Keep the **test tree non-modular** (no `module-info`
   in `src/test`) and have surefire run with `--patch-module io.github.dlbbld.ashlarchess=<test-classes>`
   so test classes are compiled/run *as part of* the main module and therefore see everything. Add
   `--add-reads io.github.dlbbld.ashlarchess=org.junit.jupiter,...` and `--add-opens` for JUnit reflection.
   maven-surefire-plugin (3.5.5, already in use) automates much of this via its module-path heuristics.
2. **Explicit `--add-exports` per internal package the tests touch.** More surgical, more brittle — every
   new internal a test reaches needs a flag. Use only if (1) proves leaky.

This is where the real effort and the only meaningful build risk live; it's contained to `pom.xml`
surefire/compiler config and breaks loudly (compile/test errors), not silently.

## 8. Risk assessment & "don't re-carve the stone"

| Item | Risk | Mitigation |
|---|---|---|
| Module name (Phase 0) | ~zero | additive metadata; no consumers yet |
| Package-by-feature reset (Phase 1) | low | mechanical, compiler-checked, no behavior change |
| Exports under-/over-scoped (Phase 5) | medium | the §4 classification pass; err toward exporting *less* (additive to widen later; breaking to narrow) |
| Test config (Phase 6) | medium effort, low correctness risk | breaks loudly; contained to build files |
| Breaking redesigns (Phase 4) | medium | the only real re-carving; isolated, reviewed, justified by the major bump |

The discipline: **20.0.0 describes the carved stone.** The boundary work is packaging discipline written
into the jar. The two breaking redesigns (sentinel records, `common.*` renames) are the *only* re-carving,
included solely because they are breaking and this is the one honest window for breaking changes.

## 9. My recommendation, in one place

1. **Ship Phase 0 as `19.0.1` now** — lock `io.github.dlbbld.ashlarchess` before anyone can depend on
   `ashlar.chess`. It's the single time-sensitive move and it's free.
2. **Run 20.0.0 as Phases 1→7**, gated on the §5 decisions.
3. **Drop Guava entirely** — done 2026-06-22 (went beyond "keep internal"): dependency removed, all use replaced
   with JDK collections, no Guava `requires` in `module-info`. ✅
4. **Keep `BitboardPosition` public** as documented advanced API rather than hiding it.
5. **Hide via non-export; keep the `*.internal` rename minimal** — the hard guarantee is `exports`, so don't
   pay for a full rename wave to get it.

### Appendix — the `module-info.java` exports (decisions resolved 2026-06-22)

```java
module io.github.dlbbld.ashlarchess {
    requires org.apache.logging.log4j;
    requires org.apache.commons.lang3;
    requires static org.eclipse.jdt.annotation;
    // Guava removed in 20.0.0 — no com.google.common requires.

    exports io.github.dlbbld.ashlarchess.board;
    exports io.github.dlbbld.ashlarchess.board.enums;
    exports io.github.dlbbld.ashlarchess.fen;
    exports io.github.dlbbld.ashlarchess.fen.model;          // Fen
    exports io.github.dlbbld.ashlarchess.pgn;
    exports io.github.dlbbld.ashlarchess.san;
    exports io.github.dlbbld.ashlarchess.adjudication;
    exports io.github.dlbbld.ashlarchess.report;
    exports io.github.dlbbld.ashlarchess.unwinnability;      // thin public face only
    exports io.github.dlbbld.ashlarchess.exceptions;
    exports io.github.dlbbld.ashlarchess.bitboard;           // BitboardPosition as documented advanced API
    // everything not listed — moves, analyze, squares, messages, common.*, board.model — is hidden by omission
}
```

Export closure verified **clean**: no exported public/protected signature references a hidden package (confirmed
both by an import-level audit and by `jdeps --api-only`). Caveat: `exports <pkg>` exposes *every* `public` class in
the package, so cross-package-internal helpers ride along unless narrowed — the Phase-3 "hide internals" polish
(quality, not a closure issue). **Pattern + progress:** narrow by moving a package's incidental publics into a
non-exported `<pkg>.internal` subpackage (kept `public`, so internal/test code still reaches them cross-package).
`bitboard` is done — only `BitboardPosition` stays exported; its engine (factory, utility, attack/move tables)
moved to `bitboard.internal`. Remaining: the `report` builders/prints, and the `pgn`/`san`/`fen` helpers.

## 11. Post-reset reconciliation (2026-06-22)

The §5.6 package-by-feature reset has **landed** (4 slices + 2 review follow-ups on `real-jpms`).
The §4 classification table above predates it: the dissolved buckets (`model`/`common.model`,
`enums`/`common.enums`, `common.exceptions`) and the single-file `fen.constants` no longer exist.
Read the current layout from `specification.md` §4 and the "Drop the Guava dependency" / package-by-feature
entries in `tasks.md`. Net: public game vocabulary is concentrated on `board`; base exceptions on top-level
`exceptions`; feature types inlined into `fen`/`pgn`/`san`; internal move types + analysis check enums in `moves`.

Two export decisions a code review surfaced, **both now resolved (2026-06-22)**:

- **`BitboardPosition` stays public → `exports bitboard` + `exports fen.model`** (the §5.1 "big call", settled).
  Both leak points — `Board.getBitboardPosition()` and `fen.model.Fen`'s `BitboardPosition` component — keep
  working for modular consumers; the appendix exports both packages. `BitboardPosition` is committed as
  documented *advanced* low-level API.
- **`analyze` / `moves` stay internal (not exported)**, so the move-analysis vocabulary stays hidden and there is
  nothing more to re-home:
  - `MoveCheck` already moved to `board` (it is the return type of the public
    `InvalidMoveException.getMoveCheck()` / `SanValidationException.getMoveCheck()`).
  - the sibling check enums `MovementCheck` / `CastlingCheck` / `KingSafetyCheck` stay in the hidden `moves` —
    fine, since their only producers (`ChessRuleAnalyzer` in `analyze`, `CastlingUtility` in `moves`) are not
    exported.
  - `board.model.UpdateSquare` (element type of the internal `perform{Promotion,Castling,EnPassantCapture}Movements`
    helpers) is never on the exported surface — no action needed.

Remaining before the descriptor ships: the Phase-3 visibility tightening (narrow incidental `public` helpers in
exported packages — quality, not closure) and the Phase-6/§7 Maven test-config (`--patch-module` for the white-box
test tree — the real build-risk part).
